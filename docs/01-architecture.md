# 01 · 总体架构

## 1. 设计约束

来自需求的硬约束，后续所有决策都受其支配：

| 约束 | 数值/描述 | 架构影响 |
|---|---|---|
| 文章量 | ≤ 100 篇/天（约 4 篇/小时） | 吞吐不是瓶颈，不需要分布式队列 |
| 部署环境 | VPS 最高 2C2G | **内存是首要约束**，模型需懒加载可卸载 |
| 站点数 | 初期 1 个，需支持扩展到 N 个 | 站点适配必须声明式，不能硬编码 |
| 标签集 | 由历史文章生成，一经生成即固定 | 生成与使用分离；运行期只读 |
| 推送 | Apprise | Python 原生调用 |
| 部署方式 | Docker + sh 一键 | 单容器，最小依赖 |
| 用户 | 多用户 + 公网 Web 管理 | 需鉴权、隔离、限流 |

一个重要的判断：**在 100 篇/天的量级上，语言与框架的性能差异不可观测。**
真正决定这个系统能否跑在 2C2G 上的，是打标后端的内存策略（见 §5）与 Playwright 是否启用（见 [03-crawler.md](03-crawler.md)）。

## 2. 分层结构

```
┌──────────────────────────────────────────────────────────┐
│  web/           FastAPI + htmx 管理端（用户/订阅/站点/审计）  │
├──────────────────────────────────────────────────────────┤
│  scheduler/     APScheduler：抓取、打标、投递、清理 四类任务   │
├───────────┬──────────────┬───────────┬───────────────────┤
│ crawler/  │  extractor/  │  tagger/  │    notifier/      │
│ 发现+抓取  │  正文+附件    │  打标降级链 │  匹配+Apprise投递  │
├───────────┴──────────────┴───────────┴───────────────────┤
│  storage/       仓储层（SQLite WAL；sqlite-vec 可选）+ 迁移  │
├──────────────────────────────────────────────────────────┤
│  core/          配置、日志、异常、领域模型、加密             │
└──────────────────────────────────────────────────────────┘
```

依赖方向严格向下。`crawler` / `tagger` / `notifier` 之间**不直接互调**，一律通过
`storage` 上的文章状态流转来解耦——这样任何一环崩溃或降级都不会连带其他环节，
重启后能从数据库状态续跑。

## 3. 流水线状态机

文章在 `articles.status` 上流转，数据库内状态转换可重入；外部通知为 at-least-once：

```
              ┌──────────────┐
              │  DISCOVERED  │  列表页/RSS 发现到 URL，尚未取正文
              └──────┬───────┘
                     │ crawler: 取页面
              ┌──────▼───────┐
        ┌─────┤   FETCHED    │  拿到 HTML，未解析
        │     └──────┬───────┘
        │            │ extractor: trafilatura / 选择器
        │     ┌──────▼───────┐
        │     │  EXTRACTED   │  正文+元数据+附件清单就绪
        │     └──────┬───────┘
        │            │ tagger: LLM 链 → 本地兜底
        │     ┌──────▼───────┐
        │     │    TAGGED    │  标签已写入 article_tags
        │     └──────┬───────┘
        │            │ notifier: 匹配订阅 → 生成 deliveries
        │     ┌──────▼───────┐
        │     │   NOTIFIED   │  终态（含"无人订阅"的情况）
        │     └──────────────┘
        │
        │     ┌──────────────┐
        └────►│    FAILED    │  保留 error/attempts；瞬时错误到期重试，确定性错误待改配置
              └──────────────┘
```

规则：

- 每个阶段是独立的调度任务，各自扫描处于对应前置状态的行做批处理
- 抓取失败立即记录为 `FAILED` 并累计 `attempts`；瞬时错误按 `next_attempt_at` 退避且达到抓取重试上限后停止
- 404、选择器失配等确定性错误不自动重试；管理员更新站点配置或执行 `nestra site sync` 时重置该站点失败文章
- 单次 HTTP 请求内部也使用有上限的指数退避；附件与通知任务另有持久化尝试上限
- `NOTIFIED` 包含"打完标签但没人订阅"——这不是失败，是正常终态
- 打标全链路失败时**不进 FAILED，停在 EXTRACTED**，等 provider 恢复后自动续跑
  （这一点很关键：API 欠费或断网不应污染数据）

## 4. 调度任务

| 任务 | 默认周期 | 职责 | 并发 |
|---|---|---|---|
| `crawl_sites` | 每站点可配，默认 30min | 发现新 URL → `DISCOVERED`；抓取 → `FETCHED` → `EXTRACTED` | 站点间串行，站内 asyncio 并发上限可配 |
| `tag_articles` | 5min | 扫 `EXTRACTED`，走打标链 | 单任务，批量 |
| `dispatch_notifications` | 2min | 扫 `TAGGED`，匹配订阅，投递 | 单任务 |
| `retry_deliveries` | 10min | 重投 `deliveries` 中失败项 | 单任务 |
| `housekeeping` | 每日 | 清理过期附件/会话/日志，VACUUM | 单任务 |

APScheduler 用 `max_instances=1` + `coalesce=True`，避免任务堆积把 2G 内存打满。

## 5. 内存策略（2C2G 的核心）

粗略预算，需实测校准：

| 组件 | 常驻内存（估算） | 备注 |
|---|---|---|
| Python + FastAPI + uvicorn | 80–120 MB | 基线 |
| APScheduler + 仓储层 | 10–20 MB | |
| SQLite page cache | 可配，建议 32 MB 上限 | |
| **LLM API 打标路径** | ≈ 0 | 只有 HTTP 请求 |
| **本地 ONNX 兜底模型** | 150–250 MB | int8 量化 bge-small-zh；**懒加载 + 空闲卸载** |
| Playwright Chromium | 300–500 MB / 实例 | 默认关闭，按站点开关 |

结论：

- **常态（LLM 链可用）：约 150–250 MB**，在 2G 上非常宽裕
- 触发本地兜底时峰值约 400–500 MB，仍安全
- 一旦启用 Playwright，必须限制 `concurrency=1` 并在任务结束后关闭浏览器；
  同时启用本地模型 + Playwright 会比较紧张，需实测

本地模型的懒加载/卸载策略：首次需要兜底时才加载，连续 `idle_unload_after`
（默认 15min）无调用则释放。这样"兜底能力"不以常驻内存为代价。

## 6. 模块边界与职责

| 包 | 职责 | 明确不负责 |
|---|---|---|
| `core/` | 配置加载与校验、结构化日志、异常体系、领域模型、字段级加密 | 任何 I/O |
| `crawler/` | 从站点发现文章 URL；下载页面 HTML；robots/限速 | 解析正文 |
| `extractor/` | HTML → 标题/正文/时间/作者/附件清单；下载附件 | 判断文章是否新 |
| `tagger/` | 文章文本 → 冻结标签集的子集 + 置信度 | 决定推送给谁 |
| `notifier/` | 订阅匹配、投递去重、调用 Apprise | 打标 |
| `scheduler/` | 编排上述四者，重试与退避 | 业务逻辑 |
| `storage/` | 仓储接口、迁移、事务 | 业务规则 |
| `web/` | HTTP 接口、鉴权、模板渲染 | 直接操作 DB（必须经 storage） |

## 7. 关键设计决策记录

**为什么不用 Scrapy？**
100 篇/天用不上它的调度器与中间件体系，`httpx` + `asyncio` 加一层薄封装即可，
镜像更小、内存更低、行为更可控。若将来站点数量与频率上一个量级，再迁移。

**为什么不用 Postgres？**
单机、单写入者、日增百行级。SQLite WAL 模式下读写并发足够，
省下一个容器约 100–200MB 内存和全部运维成本。默认 30–80 个标签用内存暴力
余弦比对即可；启用本地模型且规模增长后，可选用 `sqlite-vec` 承担向量检索。

**为什么标签集必须冻结？**
需求明确要求。技术上也更好：订阅关系绑定标签 ID，标签集漂移会让用户的订阅语义
在不知情的情况下改变。冻结后标签是稳定契约，LLM 只做"从固定集合里选"的分类任务，
可用 JSON Schema 强约束输出并校验，杜绝幻觉标签污染。

**为什么打标失败不算文章失败？**
打标依赖外部 API，欠费、限流、断网都是常态。把这类瞬时故障写成文章的终态
`FAILED`，会导致故障恢复后需要人工捞数据。停在 `EXTRACTED` 让系统自愈。
